# Mini-SGLang 开发与实验文档

## 1. 当前版本定位

本项目是教学型 LLM 推理框架，当前重点是 Tensor Parallel（TP）、TP-local KV Cache、集合通信优化和可复现实验。

当前已完成通信优化和统计基础；backend-specific KV metadata、持久化 page table、Sequence Parallel 尚未实现。

## 2. 已实现功能

### Tensor Parallel 与 KV Cache

- 使用 Column/Row Parallel Linear、Vocab Parallel Embedding。
- 主要通信是 Attention `o_proj`、MLP `down_proj` 的 `all_reduce`，以及词表 logits 的 `all_gather`。
- 每个 TP rank 保存本地 KV shard，不跨 rank 复制完整 KV Cache。

### Collective 模式

通过 `tp_collective_mode` 或 `--tp-collective-mode` 配置：

| 模式 | 说明 |
|---|---|
| `legacy` | `dist.all_gather` + tensor list，基线 |
| `tensor` | `all_gather_into_tensor` |
| `buffered` | 固定 shape 下复用 gather buffer |
| `adaptive` | 按 shape 复用多个 gather workspace；同时作为可选分块 all-reduce 的启用开关 |

### 采样模式

通过 `tp_sampling_mode` 或 `--tp-sampling-mode` 配置：

| 模式 | 说明 |
|---|---|
| `gather` | 完整 logits gather，正确性基线 |
| `distributed` | 交换 local top-k candidates，values/index 分两次 gather |
| `distributed_packed` | values 和 indices 按 bit pattern 打包，一次 gather 后解包 |
| `adaptive` | greedy 使用两次标量 `all_reduce`；`top_k>0, top_p=1` 使用 packed candidates；top-p 回退完整 logits |

`distributed_packed` 不改变 values 精度或 index dtype。top-p 等场景继续回退到完整 logits 路径。

`tp_ar_chunk_bytes=0`（默认）关闭 Prefill 分块 GEMM–AllReduce。启用后仅 adaptive、TP>1、较大 CUDA payload 且 NCCL 支持异步 collective 时尝试最多 4 个 token chunk；其余情况回退普通 `all_reduce`。当前实现是分块 GEMM 后提交异步归约并等待，不宣称 GEMM 与通信已经流水重叠；该路径尚未完成 CUDA/NCCL 实测，不提前声明收益。

### 通信统计

启用 `collective_stats=True` 或 `--collective-stats` 后，统计 `all_reduce`、`all_gather`、`broadcast`、`barrier` 的调用次数、payload bytes 和调用耗时。

统计耗时主要反映 collective 调用耗时，不等同于实际网络 wire bytes。最终性能应以同步 benchmark 为准。

## 3. 尚未实现的功能

以下功能目前不要写入实验结论：

- backend-specific KV metadata；
- 持久化 GPU page table / request slot；
- Sequence Parallel / Reduce-Scatter；
- 多机 TP；
- KV Cache FP8/INT8、offload、跨 GPU 迁移。
- adaptive 分块 GEMM–AllReduce 的 CUDA/NCCL 端到端收益验证。

当前 KV Cache 实验只能比较已有的 page size、backend 和 TP 配置。后续实现 metadata 优化时必须保留 legacy 开关。

## 6. 分布式 Benchmark

脚本：[examples/benchmark_distributed.py](examples/benchmark_distributed.py)

示例：

```bash
torchrun --standalone --nproc-per-node=2 \
  examples/benchmark_distributed.py \
  --model-path /path/to/model \
  --tp-size 2 \
  --tp-collective-mode legacy \
  --tp-sampling-mode gather \
  --warmup 5 --repeat 20 \
  --output results/tp2_baseline.json
```

优化配置：

```bash
torchrun --standalone --nproc-per-node=2 \
  examples/benchmark_distributed.py \
  --model-path /path/to/model \
  --tp-size 2 \
  --tp-collective-mode buffered \
  --tp-sampling-mode distributed_packed \
  --collective-stats \
  --output results/tp2_optimized.json
```

Benchmark 每轮执行：

```text
barrier -> device synchronize -> 计时 -> scheduler case
-> device synchronize -> 结束计时 -> barrier -> rank MAX
```

结果包括 wall-clock 和 accelerator event 的 median/P90/P99、吞吐、峰值显存及 collective stats。统计模式会引入诊断开销，最终性能结果应同时跑一份不带 `--collective-stats` 的结果。

## 8. 推荐实验顺序

固定模型、dtype、backend、prompt、page size 和输出长度，每次只改变一个变量：

1. `legacy + gather`：完整通信基线。
2. `legacy/tensor/buffered + gather`：只比较 collective 实现。
3. `legacy + gather/distributed/distributed_packed`：只比较采样通信。
4. `buffered + distributed_packed`：组合配置。
5. TP=1/2/4/8：比较扩展性。
6. page size=8/16/32/64：比较 KV page 管理影响。

建议初始矩阵：

```text
tp_size:       1, 2
input_len:     128, 512
output_len:    1, 32
batch_size:    1, 4
page_size:     16, 32
warmup:        5
repeat:        20
```

## 9. 正确性检查

先用 greedy、短输入和短输出确认 TP 不死锁：

```bash
torchrun --standalone --nproc-per-node=2 \
  examples/benchmark_distributed.py \
  --model-path /path/to/model \
  --tp-size 2 --tp-sampling-mode gather \
  --warmup 1 --repeat 3
```

之后检查：

- `distributed_packed` 编解码前后 values/index 完全一致；
- candidate `all_gather` 次数由 2 变为 1；
- top-p 仍回退到完整 logits；
- 相同输入、dtype 和配置下 baseline/optimized 生成结果一致；
- TP=1 与 TP=2 的 greedy 结果一致。

不要只根据一次运行下结论。每个配置至少保留 20 次 measured runs，并保存 JSON/CSV。

## 11. 后续开发顺序

```text
P0  保持 legacy 稳定，完善 benchmark 和统计
P1  验证 distributed_packed 的正确性与收益
P2  backend-specific KV metadata，默认保留 legacy
P3  持久化 FA page table 和 request slot
P4  CUDA Graph metadata 优化
P5  Sequence Parallel / Reduce-Scatter
P6  KV 量化、offload 和更复杂的并行策略
```

每项优化都应有独立配置、测试和 A/B benchmark，避免通信、KV Cache 和调度改动同时发生而无法定位收益。
